Orbis, explained from the ground up

An HR assistant that answers questions from two grounded sources — the company's policy documents and its employee database — and refuses to answer when it cannot show its working. This guide covers every design decision and every file.

Orientation

What it is

The one-paragraph version, then the same thing with the jargon removed.

Orbis is an AI HR co-pilot. An employee or HR administrator types a question in plain English. An LLM router reads it and decides which of three engines should answer: a retrieval-augmented pipeline over the company's policy PDFs, a natural-language-to-SQL engine over the employee database, or ordinary conversation. Policy answers come back with the document and page they came from, and pass through a hallucination filter that withholds anything the source does not support. Data answers are confined to the caller's own record unless they hold HR-admin rights. Everything is written to an audit trail.

The same thing, without the jargon

Imagine an HR helpdesk that never sleeps. Ask it "how many casual leaves do I have left?" and it looks you up in the HR system. Ask "what is the maternity leave policy?" and it reads the actual policy document and quotes the page. Ask something it cannot support with evidence, and it says so rather than inventing an answer — which matters, because a confident wrong answer about someone's notice period or harassment complaint is worse than no answer at all.

The idea worth taking away Most chatbots generate text. Orbis is built the other way round: it retrieves evidence first, generates only from that evidence, then checks the generated text against it before anyone sees it. Every layer exists to make the answer attributable.
Orientation

The problem being solved

Why not just point ChatGPT at the HR handbook?

Three things make HR a genuinely hard domain for a language model:

problem 01

It doesn't know your company

A general model has never read your leave policy. Asked about it, it will produce something plausible and generic — which is worse than useless when an employee acts on it.

problem 02

HR data is private

Salary, appraisal ratings and disciplinary records sit in a database. An assistant that can read them must be incapable of showing your record to a colleague — not merely unlikely to.

problem 03

Wrong answers carry weight

Notice periods, POSH procedure, maternity entitlement. A fabricated answer here has legal consequences, so an answer with no source is a defect.

Orbis answers each of these with a specific mechanism:

ProblemMechanismWhere it lives
Doesn't know your companyRAG over your own PDFs, with citationsrag_engine/rag_pipeline.py
Private dataRead-only DB user + post-generation scope checkrag_engine/nl_to_sql.py
Wrong answersSecond model grades the answer against the sourcerag_engine/verifier.py

The models — which, from where, and why

Four jobs, three models, one provider interface.

A common mistake is to use one large model for everything. Orbis uses a different model per job, because the jobs have genuinely different shapes: classifying a sentence into one of three buckets is not the same problem as writing correct SQL.

Why the SQL model was chosen by measurement, not reputation

Three candidates were run against the same twelve questions. The result changed the decision — the largest model was also the fastest, and a well-regarded mid-size model failed completely because it emitted reasoning prose where SQL was expected: 

openai/gpt-oss-120b          12/12   ~1.0 s/query   ← chosen
llama-3.3-70b-versatile      10/10    2.4 s/query
qwen/qwen3.6-27b              0/10    returned commentary, not SQL
A trap worth knowing about: reasoning models gpt-oss-120b "thinks" before answering, and that thinking consumes the token budget. The router originally allowed max_tokens=4 — fine for a normal model, but the reasoning model spent all four thinking and returned nothing. Every question silently fell back to small talk. Two fixes: reasoning_effort=low, and budgets that leave room for an actual answer.

One provider interface

Every model call in the system goes through three functions in rag_engine/llm.py. Swapping provider is an environment variable: 

LLM_PROVIDER=groq          # default when GROQ_API_KEY is present
LLM_PROVIDER=huggingface   # same code, different backend

This is not hypothetical tidiness. Mid-development the Hugging Face account ran out of credits and returned 402 Payment Required, taking the whole application down. Because provider selection was already isolated, the migration to Groq touched one file plus configuration.

Foundations

Key concepts

If any term below is unfamiliar, read this before the engine sections.

Embedding

A list of numbers representing a piece of text's meaning. Here, 768 numbers. Texts with similar meaning get similar numbers — which is how "am I entitled to maternity leave?" finds a paragraph that never uses the word "entitled".

Vector store

A database of embeddings that can answer "which stored texts are closest to this one?" quickly. Orbis uses ChromaDB, persisted under data/chroma/.

Chunk

Policies are too long to feed a model whole, so they're split into ~900-character pieces. Each chunk keeps its source file, page and category — the reason a citation can name a page.

RAG — retrieval-augmented generation

Instead of asking the model what it knows, you retrieve relevant text first and instruct the model to answer only from it. Turns an unverifiable claim into a citable one.

NL → SQL

Turning "how many people are in Legal?" into SELECT COUNT(*) FROM employees WHERE Department = 'Legal', then running it.

Few-shot prompting

Showing a model worked examples rather than describing rules. Orbis keeps 18 question→SQL pairs and selects the 6 most relevant per question, using the same embedding model that powers policy search.

Grounded

Every claim in an answer is supported by the retrieved text. The verifier's job is to decide this, and its verdict can suppress the answer.

Engine · 1 of 4

The router

rag_engine/router.py — 52 lines, one function, runs on every message.

The router reads the message and replies with exactly one word. Everything downstream depends on it being right, so it is deliberately the simplest component in the system. 

def decide_route(question: str) -> str:
    answer = chat(ROUTE_PROMPT.format(question=question),
                  model=settings.ROUTER_MODEL,
                  max_tokens=32)          # not 4 — see the reasoning-model trap
    word = answer.strip().lower()
    if "sql" in word:  return "sql"
    if "rag" in word:  return "rag"
    return "chat"                     # unrecognised → safest branch

Substring matching rather than equality is deliberate: a model that replies "sql" and one that replies "Answer: sql" should both work. Anything unrecognised falls to chat, the branch that cannot leak data or invent policy.

The prompt mirrors the database

The original prompt described an older schema, so "who is my manager" routed to small talk — the router had never been told manager data existed. The lesson generalises: a router must know what the system can actually answer. It now lists the real column families.

RouteTriggers onExample
sqlleave balances, appraisals, salary, manager, POSH status, headcount"who is my manager"
ragpolicy, rules, handbook, eligibility, procedure"what is my notice period"
chatgreetings, thanks, questions about the assistant"what can you do"
Measured 14 of 14 test questions routed correctly, averaging 0.32 s.

Why overlapping chunks

Chunks overlap by 150 characters because a sentence split across a boundary would otherwise be retrievable from neither half. The splitter also prefers to break at a paragraph or sentence end rather than mid-word.

Why chunk IDs are content hashes

Each chunk's ID includes a hash of its text, so an edited document produces new IDs. That has a consequence worth understanding, because it caused a real bug:

Fixed: the assistant cited a superseded policy Re-uploading an edited policy created chunks with new IDs, and the old chunks remained — so both versions were searchable and the assistant could cite the outdated rule alongside the current one. In a compliance tool this is the worst kind of bug: confidently correct-sounding and wrong. The fix is one line — index_file() now deletes by source before re-indexing.

Citations name the issuing organisation

Each chunk stores which company published the document, so a citation reads Orbis · Leave_and_Time_Off_Policy p2. This mattered because the original corpus mixed several companies' published policies — the metadata makes the provenance visible rather than implied.

Engine · 3 of 4

Natural language to SQL

rag_engine/nl_to_sql.py — the most safety-critical file in the project.

Letting a language model write SQL against employee records is the riskiest thing Orbis does. Five independent layers stand between the question and the database, on the assumption that the model will sometimes be wrong.

"how many casual leaves do I have left?"
1 · Generate with worked examples
6 nearest of 18 examples, chosen by embedding similarity
2 · Unknown-column check
invented column → regenerate once with the error
3 · Scope guard security boundary
must be a plain single-table read of the caller's own row
4 · Statement validator
SELECT only · no UNION, comments, semicolons, PersonalEmail
5 · Read-only database user
orbis_user holds SELECT and nothing else
Figure 4. Defence in depth. Layer 5 holds even if layers 1–4 are all bypassed: the account has no privilege to write.

Why worked examples replaced written rules

The prompt originally described rules in prose. Rules accumulated and began to contradict each other — the word "pending" in a leave question dragged in a POSH training filter, because a rule had explained what "pending POSH" meant. Small models follow demonstrations far more reliably than descriptions.

QuestionRules-based promptFew-shot prompt
"leaves pending for me"POSH filter + garbage3 leave balances, scoped
"casual leaves I have left"all 48 rowsCasualLeaveBalance, scoped
"when is my next appraisal"LastAppraisalDateNextAppraisalDate
"employees per department"no COUNT, no GROUP BYCOUNT + GROUP BY + ORDER

Example selection is dynamic

All 18 examples in the prompt would be noise. Instead the question is embedded — reusing the model already loaded for policy search — and the 6 nearest examples are included. Ask about leave and you get leave examples; ask about headcount and you get aggregate examples.

The scope guard, in detail

A matching WHERE EmployeeID = 'EMP1001' is not proof that a query is safe. Anything that widens the result set alongside it leaks other people's records. The guard therefore rejects far more than it accepts:

Generated SQL (caller = EMP1001)VerdictReason
… WHERE EmployeeID = 'EMP1001'allowplain single-table read of one row
… WHERE EmployeeID='EMP1001' OR Department='HR'blockOR widens beyond the caller
… UNION SELECT * FROM employeesblocksecond statement returns everyone
… WHERE EmployeeID = 'EMP10011'blockprefix of the caller's ID, different person
… WHERE ManagerID = 'EMP1001'blocktheir reports, not them
… WHERE Dept=(SELECT Dept … 'EMP1001')blocksub-select widens the outer query
The ManagerID case is instructive When employee IDs became strings like EMP1001, a naive check for "the caller's ID appears next to an ID column" would have accepted WHERE ManagerID = 'EMP1001' — quietly returning every direct report's salary to their manager. The guard now requires the column to be exactly EmployeeID. Being wrong here is not a bug report, it is a data breach.

Administrators are a separate case

Admins are not restricted to their own row — but "my leave balance" still has to mean someone. Two distinct parameters express this:

employee_id
Restricts the caller to their own row. Enforced after generation. Employees only.
caller_id
Says who "me" refers to. Enables self-queries without restricting org-wide ones. Everyone.

Before this split, an admin asking "how many leaves do I have?" got a query filtered by 'EMP1001' — a value the model had copied from an example in the schema description. It was right by accident, and would have been wrong for any other administrator.

Engine · 4 of 4

The verifier

rag_engine/verifier.py — 45 lines that can veto any answer.

After the answer is written but before anyone sees it, a second model receives the retrieved context and the generated answer, and grades one thing: is every claim supported? It must reply in a fixed shape. 

GROUNDED|0.99      → release the answer with its citations
UNGROUNDED|0.20    → replace with "I don't know based on the provided documents"

It fails closed

If the verifier cannot be reached, the answer is withheld. The original code did the opposite — an unreachable checker meant answers passed through marked "verified", which inverts the guarantee at exactly the moment it matters.

Failing closed has a cost, and it needed a second fix Once the verifier failed closed, an unrelated bug made it fail constantly: its token budget was too small for the reasoning model, so it returned nothing and every correct answer was suppressed. Two lessons — fail-closed only helps if the thing rarely fails, and "the answer was withheld" must be distinguishable from "the checker is down". The response now carries both states separately, because they are also treated differently in the audit log.

A privacy interaction worth knowing about

The audit log deliberately hides employees' question text from administrators, showing it only for blocked entries an admin must investigate. When the verifier began failing closed, every answer became "blocked" — which would have exposed every employee's questions during an outage. Two safety features, individually sound, combining badly. Separating "blocked" from "unavailable" fixed both.

Application

The security model

Three database identities, chosen so that a mistake in code cannot become a breach.

IdentityDatabasePrivilegesUsed by
orbis_userorbis_hr SELECT only The NL→SQL engine — the only identity the LLM's SQL ever runs as
orbis_hr_adminorbis_hr.employees SELECT INSERT UPDATE DELETE The admin Employees screen only. Never reachable from the AI path.
orbis_apporbis_app ALL Accounts, chats, audit. No access to HR data at all.

The separation means a hostile prompt that defeats every software check still cannot write to the database, because the connection it arrives on holds no write privilege. Software checks are the first line; database privileges are the one that has to hold.

Other controls

Sessions expire

Bearer tokens are valid 7 days and can be revoked. Sign-out invalidates server-side, not just in the browser.

Login throttling

8 failed attempts per address per 5 minutes.

Pagination capped

Hard ceiling of 200 rows per request, so no single call can pull the table.

Private columns blocked

PersonalEmail is rejected by the validator — the AI can never select it.

Errors reveal nothing

Driver messages are logged, never returned; they leak schema details.

Audit redaction

Admins see metadata for normal chats; question text only for blocked entries.

Identity and onboarding

How someone gets an account — and why they cannot simply claim one.

The vulnerability this design exists to prevent Registration originally accepted an employee_id from the request body and stored it unchecked. Anyone could sign up claiming employee 2001 and read that person's salary and appraisal history. The fix is architectural: the client never supplies an identity at all — it is derived server-side from the company email address on the HR record.
HR adds a new hire
name + personal email + department
Server allocates identity
next free EMP id · meera.krishnan@orbis.com minted from the name
Single-use invitation
random token, 7-day expiry, emailed to the personal address
New hire sets a password
/?invite=… — the link proves they hold that inbox
Account bound to the HR record
employee_id comes from the invitation, never from the browser
Figure 5. Invitation onboarding. Possession of the personal inbox is what authenticates the person — the same principle as any password reset.

Company addresses must be unique, and names are not

Addresses are generated from names, which required handling a real property of the data. The original dataset had 1,200 distinct names across 99,999 employees — one name shared by 112 people. Generation appends a suffix until the address is free, exactly as real employers do: 

rekha.tiwari@orbis.com
rekha.tiwari2@orbis.com
rekha.tiwari3@orbis.com
…
rekha.tiwari112@orbis.com   # all 112 resolve uniquely

Accents are folded (José Núñez → jose.nunez), punctuation dropped, and an empty name falls back to employee.

Two ways in, one identity source

Invited

New hires. HR creates the record; the link goes to their personal inbox. Only the inbox holder can activate it.

Self-service

Existing staff already in the HR system register with the company address HR issued. Unknown addresses are refused.

Granting admin rights

Creating the first administrator is a bootstrap problem — granting admin rights requires being an admin — so it is done on the machine, not over the network: python -m app.provision create-admin. Afterwards, admins grant access through the interface, with guardrails enforced server-side:

  • An admin cannot revoke their own access — they could not undo it.
  • The last administrator cannot be demoted — the app would become unadministrable.
  • Role changes invalidate existing sessions, so new permissions apply immediately.
  • Every change is audited.

Employees are never deleted

Departure sets Status = 'exited', disables the login and drops its sessions. Employee IDs are never reused. A deleted row whose ID was later reissued would hand a departed colleague's account to whoever inherited the number — and the audit trail references those IDs permanently.

llm.py 143 lines

The only file that talks to a language model. Two providers behind one interface, so nothing downstream knows which is in use.

  • chat() — single-turn instruction call

  • _groq_complete() / _hf_complete() — the drivers

Raises a specific LLMError per failure — bad key, rate limit, empty response — because "something went wrong" cost hours of debugging when a reasoning model silently returned nothing.

Limits and next steps

What this deliberately does not do, and what would come next.

Known limits

LimitWhy it is acceptable here
Generation is a hosted APILocal inference needs hardware this does not have. Provider is one config line.
Rate limiting is in-processCorrect for one worker; a multi-process deployment would need shared state.
Tokens live in localStorageVulnerable to XSS. Production would use httpOnly cookies.
No password resetRecovery is an operator action via the CLI.
Retrieval is dense-onlyHybrid search with re-ranking would improve recall on keyword-heavy queries.
Audit log is mutableTamper-evidence would need append-only storage or signing.

Where the work would go next

An evaluation set

~30 graded question/answer pairs to measure retrieval precision and groundedness, so prompt changes can be judged rather than guessed at.

Hybrid retrieval

Combine keyword and dense search with a re-ranking pass — the single biggest lever on answer quality.

Markdown rendering

Answers arrive with markdown emphasis that currently displays literally.

Streaming responses

Tokens as they generate would make a ~1 s answer feel instant.

The through-line Nearly every design decision here answers the same question: how do we make it impossible, rather than unlikely, for this to give someone the wrong answer or someone else's data? That is why there is a verifier as well as a careful prompt, a scope guard as well as a read-only database user, and a test suite that asserts what cannot happen.
